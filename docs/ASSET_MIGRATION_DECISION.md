# 旧版更新资产迁移决策材料

状态：待跨项目决策；本文件不授权发布或修改现有 Release。以下升级、回滚和隔离步骤均 **NOT RUN**。

## 已知事实与范围

本地源码标签 `v1.4.0` 至 `v1.4.9` 的 Runner 都包含旧安装包名称及 `SHA256SUMS.json`；其中 `v1.4.7` 至 `v1.4.9` 已进一步核对：它们请求 releases/latest，按精确名称匹配，从 JSON 按安装包名称读取 SHA-256，下载后再次计算文件哈希，未读取 GitHub API `digest`。`v1.4.0` 至 `v1.4.6` 的完整调用链尚未逐一核对。本地 `v1.0.0` 至 `v1.3.1` 标签中没有该 Runner 文件，不能据此推断它们的更新行为。当前工作树的 Runner 也采用旧资产方式。审计观察中有 1.4.10 安装及 1.4.11 稳定版，但其发布二进制尚未验证；不能声称影响版本清单完整。新版消费者尚未实现版本化资产支持。

## A：一次性过渡 Release

在跨项目明确批准例外后，先发布高于所有目标旧版的过渡版本；它至少需要旧名称的安装包和包含该名称及其哈希的 `SHA256SUMS.json`，供旧 Runner 发现。过渡安装器必须安装已实现并测试新格式的 Runner 和应用更新入口，且先验证原目录升级。待目标用户完成过渡，再发布仅使用 `<ProductId>-<version>-Setup.exe`、同名 `.sha256` 和 GitHub API SHA-256 digest 的正式版本。无法证明所有离线或长期未运行实例均已过渡，不能假定所有旧版仍能自动升级；需提供手动路径。

冲突及批准范围：统一规范第 9 节要求每个稳定 Release 的唯一可安装资产采用版本化名称，并要求同名 `.sha256` 和 API digest；旧名称不符合该命名规则。若同一过渡 Release 同时发布旧名与版本化安装包，则违反只有一个可安装资产的数量要求。若只发旧名，则缺少规范指定的版本化安装包和同名校验文件。旧更新器依赖 JSON 而非 API digest 的行为也不能满足工具箱自动安装/更新的 digest 要求；例外不能声称旧客户端具备该校验。例外应限定具体版本、期限、资产、受影响客户端和撤销条件，并按规范第 13 节先协调跨项目流程。

隔离验证：在可还原的 Windows VM 快照中分别安装每个受支持旧版，使用独立测试 Release 源或受控网络镜像，记录实际请求、资产匹配和哈希；升级到过渡版本，核对原目录、登记、Manifest、EXE 版本与数据；再切换到仅新格式的测试 Release 验证再次升级和 digest 缺失/错误时拒绝。测试并发、UAC 拒绝及离线状态。回滚使用 VM 快照或经过验证的完整安装目录、登记和用户数据备份恢复；不要假设旧安装器能安全降级。

## B：用户手动运行新安装器

发布符合规范的新安装器，用户从可信 Release 下载并核对 digest/校验文件，然后由安装器查询 HKLM/HKCU 的 32/64 位视图，识别唯一登记的 `InstallLocation`，确认 appId、Manifest、主程序和路径一致；有多条冲突或登记损坏时停止并提示修复，不猜测新路径。升级只能覆盖确认的原目录。安装器需显式保留 `%LOCALAPPDATA%` 下用户数据和其他产品目录。当前安装器尚未完全实现这些保证，不能把本方案视为可执行。

机器安装需要管理员授权：正常请求 UAC；无管理员凭据或拒绝时停止，不尝试绕过 UAC、写入其他目录或创建用户级第二实例。必要时由管理员协助。

隔离验证：在分别含有效登记、损坏登记、多视图冲突、Unicode 原目录及无管理员权限的 VM 快照中运行安装器，验证只更新原目录、拒绝冲突、UAC 拒绝无副作用，并比较安装前后用户数据及其他产品文件的哈希。对旧版本逐一重复并验证离线场景。回滚先还原 VM 快照；部署前另行验证备份恢复，不能假设降级安全。
